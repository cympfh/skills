# nihongo

日本語は読み手が読み返さずに「誰が、何を、どの条件で、どうする」か追えるように書く。きれいに見せることより、意味が動いていないことを優先する。

コード、コマンド、識別子、引用、画面の項目名は変えない。整えるのは地の文だけである。

推敲では著者の主張と文体を保ち、不自然な箇所だけを直す。新規では最初からこの規則で書く。

## 規則がぶつかったとき

上から順に従う。

1. 事実、数値、固有名詞、否定、条件、期限を根拠なく足したり落としたりしない。根拠はユーザーの依頼、開いたファイル、実行結果、この会話で確定した事実に限る。
2. 断定、推量、許可、能力、義務、保証を互いに入れ替えない。
3. 読み手が動作主と掛かり先を追える形を優先する。短さはその次である。
4. チャット、手順、仕様、報告、差分説明、コミットメッセージは、用件を直接書く。緩急は足さない。
5. 章、記事、解説など、読み物として読ませる文章にだけ、あとの「読み物の緩急」を足す。迷ったら足さない。材料がなければ平坦なまま残す。

## 書く前に決める

- **用件**: 読み手に、何を知って、何をすればよいか。
- **立場**は一つに決める。文ごとに働きが違うときは、文末で分ける。
  - **説明**: 事実、結果、考え。完了は「〜した」、現在の動作は「〜する」、方針は「〜する方針だ」、予定は「〜する予定だ」。方針を「〜します」と書くと、これからやる作業に見える。
  - **決まり**: 「〜する」「〜してください」。勧めの「〜しましょう」にしない。理由を述べる「〜が重要だ」は理由のまま残す。
  - **勧め**: 動くのは読み手。「〜しましょう」「〜してください」。書き手の予定である「〜しておきます」にしない。「〜しなければならない」へ上げない。
- **文体**は「です・ます」か「だ・である」のどちらか一つ。文書の途中で混ぜない。周囲の文書に合わせる。指定がなければ、ユーザーへの返答は「です・ます」、仕様や設計メモは周囲に合わせ、なければ「だ・である」。
- 読み物か、実務の文か。手順や報告を、記事の語りに変えない。

頼まれた文体は壊さない。エッセイや小説では、何を何に例えたか読み取れる比喩を残す。主語と述語が成り立たず、何を言いたいかも連想できない比喩だけを直す。紹介や宣伝を頼まれたときは、短い評価の重ねや「ぜひ」を残す。事実と違う誇張は事実のように書かず、根拠をユーザーに尋ねる。メールの宛名、挨拶、署名は削らない。

## どの文章でも守る

### 意味を動かさない

- 意見（〜と思う）を事実として言い切らない。伝聞（〜とされる）を断定にしない。例えを、例えた物が事実であるように書かない。仮定の条件を外して予定にしない。反語を、ただの疑問にしない。
- 「〜してよい」（許可）、「〜できる」（能力）、「〜しなければならない」（義務）、「必ず」「保証する」（保証）を互いに替えない。「〜場合がある」を消して言い切らない。
- 「〜だけ」「〜でない場合」「〜なら」の掛かる範囲を落とさない。「全員が賛成したわけではない」を「全員が反対した」にしない。
- まだ分かっていないことは、分かったように書かない。未定や調査中はその状態のまま書く。本文に「要確認」と入れない。読み手に渡す事実が足りないときは、ユーザーに一度だけ尋ねる。尋ねられないときは、分かっている範囲だけを書き、推測で埋めない。
- 根拠のない数値、原因、担当、例を足さない。相対的な「昨日」は、書いた日が本文か依頼から確定するときだけ日付を添える。

悪い: 予算が通れば来月から始められる。 → 来月から始める。
良い: 予算が通れば、来月から始められる。

悪い: 原因は設定の誤りだとされる。 → 原因は設定の誤りだ。
良い: 原因は設定の誤りだとされる。

### 誰が何をするか

- 読み違える位置にだけ、「誰が・何を・どうした」を書く。すでに追える文へ主語を足さない。システムの動作を、人の行為に変えない。
- 主題の「〜は」「〜では」は文末まで掛かる。後半が別の主体の動作なら、後半の頭にその主体を書く。どちらか決められなければ、主体を作らない。
- 目的語のない他動詞の前に、比較や条件を挟まない。「設定の一覧を渡して比べさせると、Aは残りの案より多く削った」は、何を削ったのかが「設定の一覧」に読める。対象が分かっていれば目的語に書き、分かっていなければ「Aが削った量は、残りの案より多かった」のように動作を名詞にする。「〜を行う」にはしない。
- 動作を名詞の主題にして、必要なことを述語にすると、主語と述語が噛み合わない。「ログの一括削除は、権限も変える必要がある」は「ログを一括で削除するには、権限も変える必要がある」。
- 漢語を助詞なしで詰めない。「書類不備発見時は」は「書類の不備を発見したときは」。ログイン画面のような定着した複合語はそのままにする。
- 「確認する」を「見る」のように、意味の幅が広がる言い換えをしない。
- 指す先が一つに決まるときだけ、指示語（これ、片方）を名詞に戻す。決まらなければ指示語のまま残し、決めたふりをしない。
- 道具や概念に感情や意志を持たせない。「コードが仕様を語る」は「ドキュメントに仕様が書かれている」。道具の客観的な動作（「このツールはログを集める」）はそのまま書く。人の判断を抽象名詞の作用にしない。「見積もりの甘さが判断を遅らせた」は「見積もりが甘く、判断が遅れた」。

### 一文の形

- 目安は平均で30〜45字、読点は一文に0〜2個である。この範囲に合わせるためだけに、文を分けたりつないだりしない。
- 60字を超えて、手段・理由・順序・対比が追いにくいときだけ分ける。分けた後ろの文にその関係（そのため、一方で）を残す。
- 「〜するために〜する」は分けない。分けると、目的と動作の向きが変わる。
- 「〜ます。」で終わる短い文を三つ以上続けない。同じ対象の話は一文にまとめてよい。並列の手順、担当と結果、独立した変更点は、箇条書きのまま残す。
- 10字未満の文をリズムのためだけに続けない。
- 短い主語・目的語・主題の直後に、間を作るだけの読点を置かない。

悪い: 古いキャッシュが、重複して読み込まれる。
良い: 古いキャッシュが重複して読み込まれる。

長い主語のあと、主題のあとに別の動作主が来るとき（「会議では、担当者が説明した」）、条件（「切れた場合は、」）、並べ、外すと掛かり先が変わるとき（「店長は、慌てて逃げた客を追いかけた」）は、読点を残す。

- 助詞で切るコピーを書かない。「資料を、全員へ。」は「資料を全員に渡す。」のように、述語まで書く。何をするか決まっていなければ、具体的な動詞を作らない。
- 評価の語だけを並べない。「速い。軽い。安い。」は、対象が分かっていれば「このツールは速く、軽く、安い。」宣伝を頼まれたときだけ、短い評価の重ねを使ってよい。
- 「変わったのは、画面、帳票、通知。」のように「〜のは、」のあとに名詞だけを並べて終えない。前提が前の文になければ「画面と帳票、通知が変わった。」と述語に戻す。
- 「〜を行う」「〜することが可能です」「〜を実現することができます」を新しく増やさない。「値を代入する」「高速化できる」と書く。公用文、契約、仕様、論文でその語が正式な用語なら残す。

### 語

比喩や造語で済ませず、何がどう変わるかを書く。意味の幅が同じ語へだけ替える。幅が変わるなら、曖昧な語を残すより、分かっている事実だけを書く。

| 書かない | 書く |
|---|---|
| データが静かに壊れる | 気づかないうちにデータがおかしくなる |
| 安全側に倒す | 安全を優先する |
| 時間を溶かした | 時間がかかってしまった |
| 問題を一つずつ潰す | 問題を一つずつ直す |
| 地味に効く | 目立たないながらも役に立つ |
| 例外を上に逃がす | 例外を呼び出し元へ渡す（行き先が分かっているとき） |
| 解像度が上がる、手触り、意思決定OS | どこまで分かっているか、操作した感じ、判断の枠組み |

- 「うっかり」の不注意、「ようやく」の待ちくたびれた感じ、「〜てしまった」の後悔は、語を替えても残す。「確実に」「必ず」「劇的に」へ強めない。
- 定着した慣用句（骨が折れる、手を焼く、目から鱗が落ちる）はそのまま使う。
- 役割を大げさな名詞で呼ばない。ルールを「契約」、比較の基準を「正本」、確認を「ゲート」、一覧を「台帳」と呼ばない。法的な契約、文書の正本、正式名称の品質ゲート、会計の台帳は、その意味のまま使う。
- 「本質」「核心」を「目的」にすり替えない。空疎な「本質的な」は削る。論点そのものなら「いちばん肝心な点」と言うか、そのまま残す。
- 専門の対象はその分野の用語で書く。状態を表す旗はフラグ、産業用ロボットの腕はアームである。画面の項目名、識別子、日常語はそのままにする。ソフトウェアの「版」は「バージョン」と書く。出版物の「第2版」はそのままにする。
- 補助動詞と形式名詞の「事」「為」はひらがなにする。してください、できる、みる、いただく、こと、ため。「事の経緯」のような中身のある「事」は漢字のままにする。
- サーバとサーバーのようなゆれは、周囲の文書の方針に従う。方針がなければ、一つの文書の中で一つにそろえる。

前置きは削って本題から書く。評価が主張そのものなら、述語に残す。

悪い: 結論から言うと、このボタンを押すだけで完了します。
良い: このボタンを押すだけで完了します。

悪い: 重要なのは、画面の見た目ではなく、データの形です。
良い: 画面の見た目ではなく、データの形が重要です。

- 意味のある「AではなくB」は残す。「Bに加えてA」や「AよりB」にしない。
- 「Aではない。Bでもない。Cだ。」で、AとBが読み手の誤解でないなら「Cだ。」と書く。誤解を退けるなら「AやBではなく、Cだ。」の一文にする。
- 「もちろん、失敗もする。」のような先回りの短い譲歩は、「もちろん、」を外す。認めている内容は残す。会話、引用、「AはもちろんB」はそのままにする。
- 中身のない結びを書かない。「いかがでしたでしょうか」「ぜひ参考にしてみてください」「参考になれば幸いです」「ご質問ありがとうございます」。チャットの返信も定型の礼から入らず、用件の一文から始める。読み手が次にすることを伝える結びは残す。

### 段落とつなぎ

- 一段落一話題。話題が違えば分け、違う話題を一つの段落にまとめない。文の順序は時間と前提が崩れない範囲で動かす。
- 「しかし」「また」「つまり」「そのため」は、つないでいる二つの中身を指せるときだけ使う。因果がなければ「これにより」でつながない。
- 予告だけの文を書かない。

悪い: 注目すべき点があります。再起動が必要です。
良い: 再起動が必要です。

- 「理由は三つあります」は、長い手順で項目数そのものが案内になるときだけ残す。短い文章では項目を直接書く。数と項目が食い違う予告は、数を合わせにいかず、項目をそのまま書く。
- 本文と同じことを「まとめると」で繰り返さない。その文にしかない数値、条件、例外は残す。報告の最後で、次にすることを書く文は残す。
- 見出しはその節の中身が分かる短い名詞句にする。「保存期間」「削除後の復元」。警告、条件、期限は見出しに閉じ込めず本文に書く。「〜について」と、見出しの中の読点は付けない。文書の題は頼まれない限り変えない。
- 読者の行動範囲を変える文は残す。「この手順では退職の手続きは扱いません。窓口は人事です。」書き方の方針だけを述べる文は書かない。「ここでは専門用語を使わず、やさしい調子で書きます。」

### 書式

- 絵文字、文末の装飾のコロン、ダッシュ（— ― ─ ━ ──）を地の文に使わない。区切り線、図の罫線、ラベルと値のコロン（日時：10時）は残す。
- 同じ意味の言い換え括弧を付けない。「不自然な日本語（いわゆるAI臭さ）」は「AI特有の不自然な日本語」。手順を括弧に押し込まない。「編集します（先にバックアップを取ってください）」は、行う順に文を分ける。
- 箇条書きの頭を、分類語や出来事の名詞でラベルにしない。

悪い: **応答速度の低下**: ピーク時に3秒を超えた。
良い: 応答が遅くなり、ピーク時に3秒を超えた。

名前と値、引数と説明の対応（`timeout`: 秒で指定する）はラベルを残す。太字は要点にだけ使い、見出しの代わりにしない。`**` のすぐ内側を括弧や句点にしない。括弧の中だけを太字にする。句点は太字の外に出す。

## 読み物の緩急

章、記事、解説など、読み進める文章にだけ使う。手順、仕様、報告、チャット、差分説明には使わない。迷ったら、この節は使わない。

緩急は情報を減らすことではない。読者の認知を具体の観察、判断の保留、断定、具体への戻り、のあいだで切り替える。材料は対象の事実、データ、発言、書き手が実際に持っている判断だけから取る。状況に材料がなければ、何も足さず平坦なまま残す。

- 段落の基本は短い事実で立て、やや長い文で流し、短い判断で止めることである。短文は中身のある文に限る。評価語だけの断片で拍を作らない。
- 断定が三つ続いたら、具体か、実際に未確定な一点を挟む。演出の「〜に違いない」「〜だろうか」は足さない。未確定なら、未確定だと書く。
- 密な段落が二つまたは三つ続いたら、確定したことを一行で固定するか、次に見る対象を一つ出す。
- 具体（数値、ログ、発言、コードの挙動）の段落と、その意味を一段引いて述べる段落を交互に置く。
- 冒頭の数文で、読み続ける理由を一つ作る。読者の実感、検証できる問い、あとの本文が試す命題のどれか。態度のない議題表は書かない。

悪い: 本章では原因、対策、残件を扱う。
良い: タイムアウトの原因は再試行の回数ではなかった。

- 節の頭で「本節では〜を扱う」と宣言しない。前の節が残した問い、読者が持ちそうな反問、具体的な事実から入る。前の節の末尾に「次は〜を見る」と書かない。
- 理論や用語は、読者がまだ名前のない違和感を持ったあとに出す。先に定義を置いて、例で確認する順にしない。
- 分類を列挙したら、各項目をすでに出した具体へ一つずつ着地させる。着地の言い方を「一つめは」「二つめは」で揃えない。
- 途中の問いは放置しない。閉じるか、閉じていないと分かる位置に残す。
- 結ぶときは、積んだ抽象を冒頭の具体へ戻す。読者がすでに持っている事実へ戻してもよい。一般論のまま終えない。読み物では、問いを一つだけ開いたまま残してよい。実務の報告は次の動作で閉じ、問いを残さない。
- 読者への呼びかけ、依頼、断りは、冒頭か結びだけに置く。
- この節の装置の名前（緊張、回収、拍、答えの半分、緩急）を本文に書かない。これからする操作を宣言しない。「先に答えの半分を置く」は、答えの前半を内容として書けば足りる。

対象の事実か、書き手の実際の判断を更新する文だけを残す。文書の進み方だけを述べる文は書かない。

書かない: 「ここまでだと概念の説明に見える。なので例に戻す。」「この章の主題は手順ではない。」「次はログを見る。」

残す: 具体的な誤読を引用して退ける文。読者の作業範囲を限る文。例の枠を開く「ここでは、次のログを使う。」と、例を閉じる文。

短くするために、必要な範囲、比較の軸、未確定事項を削らない。密度を上げるのは、その文脈を共有したあとに限る。

## 出す前に見る

1. 各段落の頭の文が事実、判断、依頼のどれかを更新しているか。文書の予定だけなら削る。
2. 「〜は」「〜では」が後半の別の動作を巻き込んでいないか。目的語のない動詞の前に、比較や条件が挟まっていないか。
3. 数値、固有名詞、否定、期限、「だけ」「場合」を根拠なく増減していないか。許可、能力、義務、保証が入れ替わっていないか。
4. 「です・ます」と「だ・である」が混ざっていないか。絵文字、ダッシュ、間のための読点、中身のないコロンがないか。
5. 読み物なら、節末の「次は〜」と、このスキルの用語の漏出を消す。同じ調子の段落が四つ以上続いていないか。

直すときは、問題の箇所だけを直す。すでに追える文は残す。
